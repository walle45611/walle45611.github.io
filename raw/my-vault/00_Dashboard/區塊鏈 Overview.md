# 區塊鏈 Overview

區塊鏈結合密碼學、P2P 網路、分散式帳本與共識機制，讓參與者在不依賴單一帳本管理者的情況下驗證交易、協調交易順序。理解它時，需要同時考慮資料結構、網路、經濟誘因與治理。

## 系統架構與信任

| 架構 | 核心概念 | 優點 | 主要取捨 |
| --- | --- | --- | --- |
| 中心化 | 控制權由單一組織掌握 | 管理與協調容易 | 依賴中心的可信度，須處理故障與審查風險 |
| 分散式 | 多台機器共同提供服務 | 可用性、擴展性、地理備援 | 同步、一致性、網路延遲與維護複雜度 |
| 去中心化 | 控制權分散到不同參與者 | 減少單一機構控制與審查 | 惡意節點、信任建立與協調成本 |

**分散式描述機器與服務的分布，去中心化描述控制權的分布。** 單一公司可以經營跨地域的分散式系統；中心化管理也不代表只有一台主機或一份資料。

商業系統的安全需求包括身份驗證、資料保護、交易紀錄、防偽造、防竄改、不可否認性、備份與緊急應變。CIA 三要素分別是：

- **Confidentiality（機密性）**：僅允許授權者存取資料。
- **Integrity（完整性）**：資料未被未授權修改。
- **Availability（可用性）**：授權者需要時能使用服務。

MFA／2FA 保護登入，HTTPS／TLS 保護傳輸，WAF 協助阻擋網站應用層攻擊，操作日誌支援稽核，備份支援復原。區塊鏈仍需要這些系統與操作層的防護；公開帳本本身不提供資料機密性。

## 區塊、雜湊與交易驗證

區塊通常包含標頭（Block Header）與交易資料（Block Body）。以 Bitcoin 為例，標頭包含版本、Previous Block Hash、Merkle Root、Timestamp、難度目標的編碼與 Nonce。

| 元件 | 作用 |
| --- | --- |
| Previous Block Hash | 引用前一區塊，形成鏈結 |
| Merkle Root | 承諾區塊內的交易內容 |
| Timestamp | 記錄區塊的大致時間 |
| Nonce | 礦工可調整的欄位之一，用來嘗試不同雜湊結果 |
| 難度目標 | 有效 PoW 的區塊雜湊必須不大於目標值 |

密碼學雜湊將輸入轉為固定長度摘要，要求難以反推原文、難以找到碰撞，且輸入的小變化會使輸出大幅改變。修改交易會改變 Merkle Root 與區塊雜湊，使既有後續區塊的引用不再匹配；阻止攻擊者重建並取代歷史，還需要共識機制。

Merkle Tree 將交易雜湊逐層成對合併，最後得到根雜湊。驗證單筆交易只需該交易與路徑上的兄弟雜湊，證明大小約為 $O(\log n)$；512 筆交易的平衡樹需要約 9 個路徑雜湊。

- **Full Node**：自行驗證交易與區塊規則；可保留完整歷史，也可在驗證後裁剪舊區塊資料。
- **SPV（Simplified Payment Verification）**：主要保存區塊標頭，向其他節點取得 Merkle Proof，確認交易被納入某個區塊。Bitcoin 標頭為 80 bytes；SPV 較省資源，但不等同完整驗證所有交易規則。

## 金鑰、數位簽章與編碼

公鑰可以公開，私鑰必須保密。公鑰加密與私鑰解密用於保密；私鑰簽章與公鑰驗證用於驗證訊息來源及完整性，兩者用途不同。

交易簽章流程：**交易內容 → 計算簽章用摘要 → 私鑰簽章 → 節點以公鑰驗證**。簽章證明對應私鑰的控制者授權了訊息，不直接證明現實世界身份；不可否認性也依賴私鑰保管及身份綁定。

| 技術 | 概念與用途 |
| --- | --- |
| 陷門函數 | 正向容易，沒有秘密資訊時反向困難；持有陷門資訊可有效反向計算 |
| RSA | 與大整數分解問題相關的公鑰密碼系統 |
| ECC | 以橢圓曲線上的數學問題建立金鑰與簽章機制；Bitcoin 使用 secp256k1 |
| Base64 | 將二進位資料轉成文字的編碼，不提供加密保護 |

RSA 的基本金鑰關係為：選取不同質數 $p,q$，計算 $N=pq$ 與 $\phi(N)=(p-1)(q-1)$，選擇與 $\phi(N)$ 互質的 $e$，求得 $ed\equiv1\pmod{\phi(N)}$ 的 $d$。公鑰為 $(e,N)$，私鑰包含 $d$；這只是數學基礎，實際使用還需要安全的填充方案。

Bitcoin 傳統 P2PKH 地址由公鑰計算 $\operatorname{HASH160}=\operatorname{RIPEMD160}(\operatorname{SHA256}(public\ key))$，加上版本與 checksum，再以 Base58Check 編碼。其他地址類型使用不同格式。

Base64 每 3 bytes 編成 4 個字元，長度約增加三分之一；不足組時使用 `=` padding，使輸出長度為 4 的倍數。

## P2P 網路、帳本同步與拜占庭容錯

交易由使用者簽署並廣播，節點驗證簽章、可花費資金與協議規則，再由出塊者納入區塊。其他節點獨立驗證區塊，依共識規則更新帳本。

P2P 網路的基本工作是節點發現、資料傳播與同步：

| 機制 | 功能與限制 |
| --- | --- |
| Bootstrap Node | 協助新節點找到其他 peers；入口角色本身不賦予共識控制權 |
| DNS Seeds | 透過 DNS 提供可連線節點位址 |
| Known Peers | 本地保存的已知節點清單，可用於重新連線 |
| Gossip | 節點向鄰居轉送新資料，逐步擴散；存在重複傳輸與延遲 |
| Synchronization | 請求缺失區塊並驗證，依共識規則選擇有效歷史 |

新節點通常先透過已知入口取得 peers，再建立其他 P2P 連線。使用多個來源與分散連線可降低入口依賴與被隔離風險。P2P 不要求所有節點互相直連。

網路延遲、節點離線、同時出塊與網路分割，都可能讓節點暫時看到不同帳本。這種暫時分叉與協議規則變更造成的分叉，需要分開理解。

**拜占庭將軍問題**討論部分節點說謊、傳送矛盾訊息或不回應時，誠實節點如何達成一致。需要兼顧 Safety（不接受互相衝突的結果）、Liveness（系統能繼續前進）與容錯。

在典型 PBFT 的假設下，容忍 $f$ 個拜占庭節點需要 $n\geq3f+1$。PBFT 的主要階段是 Pre-Prepare、Prepare、Commit，通訊量約為 $O(n^2)$。這不是所有共識模型都適用的通用門檻；開放公鏈還必須處理身份可任意建立的 Sybil 問題。

## 共識、資源成本與確認

| 項目 | PoW（工作量證明） | PoS（權益證明） |
| --- | --- | --- |
| 參與者 | Miner，礦工 | Validator，驗證者 |
| 參與基礎 | 計算工作量與算力競爭 | 質押資產與協議的驗證者選擇規則 |
| 安全成本 | 硬體、電力與重建歷史的工作量 | 質押資產、獎懲及協議限制 |
| 主要取捨 | 能耗、礦池集中、硬體門檻 | 質押集中、委託風險、協議複雜度 |

PoW 礦工反覆調整 Nonce 等資料，直到區塊雜湊滿足目標。Bitcoin 選擇有效鏈中**累積工作量最大**的鏈，並非單純比較區塊數。PoS 的出塊與懲罰方式因協議而異，不能概括為「持幣越久越有權」。共識機制本身也不能單獨決定交易容量。

- **Staking**：將資產質押以參與共識，可類比保證金。
- **Slashing**：部分 PoS 協議對特定違規行為罰沒質押資產。
- **Staking Pool**：匯集參與者資產或驗證服務，降低個別參與門檻，但增加營運者與集中化風險。
- **Gas Fee**：使用者為執行交易或合約支付的費用，與質押不同。

PoW 的簡化追趕模型中，令 $p$ 為誠實方找到下一區塊的機率，$q$ 為攻擊者的機率，$p+q=1$，$z$ 為攻擊者落後區塊數。在固定算力比例且無限時間的模型下，追上誠實鏈的機率為：

$$
q_z=\begin{cases}
1, & p\leq q,\\
\left(\frac{q}{p}\right)^z, & p>q.
\end{cases}
$$

當 $p>q$，落後越多，追上的機率越低。這是已知落後距離的追趕模型，不等同考慮確認期間攻擊者進度後的完整雙花成功率，也不代表低於 50% 算力就沒有攻擊機會。

## Bitcoin、Ethereum 與擴展層

| 項目 | Bitcoin | Ethereum |
| --- | --- | --- |
| 起源 | 中本聰於 2008 年提出點對點電子現金方案 | Vitalik Buterin 於 2013 年提出白皮書 |
| 設計重點 | 點對點支付、稀缺性與價值移轉 | 可程式化合約與去中心化應用 |
| 帳本模型 | UTXO：追蹤尚未花費的交易輸出 | 帳戶：維護餘額、nonce、程式碼及儲存狀態 |
| 執行機制 | 功能受限的 Bitcoin Script | EVM，支援通用合約邏輯並以 Gas 限制執行資源 |
| 共識 | PoW | The Merge 後採用 PoS |

Bitcoin 的目標平均出塊時間為 10 分鐘，每 2016 個區塊調整難度，供應上限約 2100 萬枚。礦工收入包括區塊補貼與交易手續費。Hashrate 表示每秒雜湊嘗試次數：$1\ \mathrm{TH/s}=10^{12}\ \mathrm{H/s}$、$1\ \mathrm{EH/s}=10^{18}\ \mathrm{H/s}$、$1\ \mathrm{ZH/s}=10^{21}\ \mathrm{H/s}$。

Bitcoin 地址提供的是假名性，公開交易仍可被關聯分析，不能視為完全匿名。UTXO 的選取、消費與找零流程見 [[UTXO]]。

Ethereum 的基本帳戶類別為由私鑰控制的 EOA 與由程式碼定義行為的合約帳戶。EVM 執行智能合約，可支援 DApp、DAO、DeFi 與 NFT；圖靈完備描述通用計算能力，實際交易仍受 Gas 等資源限制。

The Merge 將 Ethereum 的共識由 PoW 改為 PoS，主要改變安全機制並降低能源需求，並不直接增加交易容量或保證降低 Gas Fee。

| 技術 | 用途與取捨 |
| --- | --- |
| Lightning Network | Bitcoin 的支付通道網路，將多次支付移至鏈下，以主鏈處理通道建立與結算等操作 |
| Ordinals／Inscriptions | 為 satoshi 編號並關聯寫入 Bitcoin 交易的內容；增加用途，也消耗區塊空間與儲存資源 |
| Layer 1 | 基礎鏈，提供共識、安全與結算等服務 |
| Layer 2 | 依賴 L1 安全或結算的擴展機制；具體信任假設依方案而異 |
| Optimistic Rollup | 透過可挑戰的狀態主張與爭議機制驗證結果，提款通常涉及挑戰期 |
| ZK-Rollup | 使用有效性證明驗證狀態轉換；提款時間仍取決於具體實作 |
| Dencun／EIP-4844 | 引入 blob 資料空間，降低 rollup 資料發布成本；blob 資料不由共識節點永久保存 |

## 治理與協議演進

**共識決定如何依既有規則接受區塊；治理決定規則如何制定、修改與採用。** 治理涵蓋規則制定、技術升級、協調、爭議解決與激勵調整。

開發者提出設計與實作，礦工或驗證者生產區塊，節點營運者決定運行哪些規則；使用者、代幣持有人、交易所、基金會及監管者，也能透過採用、市場或制度影響治理。

| 治理層次 | 關注內容 |
| --- | --- |
| Protocol | 區塊規則、費用模型與驗證條件 |
| Client／Software | 客戶端實作、版本與升級採用 |
| Community | 開發者、節點與社群如何討論及協調 |
| Economic／Market | 市場流動性、應用、資金與經濟誘因 |

鏈下治理透過論壇、GitHub、郵件群組與會議協調，彈性較高，但程序與影響力可能不透明。鏈上治理將提案、投票或執行規則納入協議，流程較可追蹤，但仍面臨大戶控制與投票冷漠；是否自動執行取決於設計。

Bitcoin 的治理傾向保守與粗略共識，Ethereum 則較重視持續升級與生態系協調。這些是治理風格的概括，不能取代對具體提案及參與者的分析。粗略共識不等於固定比例的正式投票。

- **Soft Fork**：收緊有效性規則，使新規則下的有效區塊仍可被舊規則接受，但舊節點不會驗證新增限制。
- **Hard Fork**：變更可能使新規則接受的區塊不被舊規則接受；若參與者採用不同規則，可能形成持續分鏈。

分叉既可能是技術升級，也可能反映治理分歧與退出選擇。The DAO 事件呈現歷史不可變更的理念與干預修復之間的衝突；重大漏洞是否及如何修復，同樣涉及治理。

## 安全層次與攻擊面

| 層次 | 主要風險與保護重點 |
| --- | --- |
| Key | 私鑰與助記詞外洩、保管及復原 |
| Wallet | 釣魚、惡意授權、誤簽交易 |
| Client | 軟體漏洞、版本不一致、錯誤更新 |
| Network | 惡意 peers、隔離、分割與傳播延遲 |
| Consensus | 雙花、鏈重組與共識失效 |
| Governance | 提案操控、影響力集中、倉促升級 |
| Economic | 攻擊成本、收益與誠實參與誘因 |

| 攻擊 | 核心手段 | 主要影響 |
| --- | --- | --- |
| Sybil（女巫） | 建立大量身份或節點 | 影響節點發現、連線或按身份計票的機制 |
| Eclipse（日蝕） | 控制目標節點的對外連線 | 隔離其網路視角，延遲或過濾資訊 |
| Partition（分割） | 阻斷不同節點群的通信 | 造成不同網路區域暫時不一致或停止進展 |
| 多數算力攻擊 | 在 PoW 中掌握優勢算力 | 可重組歷史、審查或雙花，但不能偽造他人的有效簽章 |

PoW／PoS 讓共識影響力綁定資源，降低大量免費身份取得共識權力的效果，但不會自動消除網路層的 Sybil 或 Eclipse 風險。PoS 的攻擊門檻需按具體協議與攻擊目標分析，不宜一律稱為 51%。

**Nakamoto Coefficient（納卡摩托係數）**衡量達到指定控制或破壞門檻所需的最少獨立實體數；解讀時必須說明衡量的子系統與門檻。

協議安全不等於使用者資產操作安全。私鑰外洩、釣魚與錯誤授權可能繞過共識層的保護；治理與經濟誘因也都是系統安全的一部分。
