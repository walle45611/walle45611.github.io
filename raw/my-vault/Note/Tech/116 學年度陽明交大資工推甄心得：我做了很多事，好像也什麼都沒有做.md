這篇文章想記錄一下自己這次研究所推甄的經歷，包含筆試、面試、過去做過的專案，以及一些事後的反思。其實當初我並沒有打算參加推甄，是後來認識了蘇仕文教授，在他的鼓勵下，才決定試試看。

大學期間，除了課業之外，我也在大二、大三、大四的不同時期，先後擔任三個計畫的助理，另外還有一份投入程度已經接近正職的工作。這幾年做過的事情，從前端、後端、自動化測試，一路到 AI Agent、網路設備與機房維運都有。下面也會整理這些經歷，說明我到底把時間花在了哪裡，以及後來遇到的時間分配問題。

這次我總共申請了國立陽明交通大學四個研究所招生組別，最後拿到的結果分別是：

至於另外兩個志願，交大資聯與智慧科學暨綠能學院碩士班聯招，結果都是不錄取。但這兩個結果，我其實不太意外。畢竟這兩個招生管道都會看在校成績，而這部分剛好是我最沒有優勢的地方。雖然有一些專題、論文、競賽和工作經驗，但我也知道，這些成果不一定能夠彌補在校成績上的不足。當然，我並不知道實際審查時各項資料的評分情況，也不能斷定自己就是因為成績不好才沒有錄取。只是以自己的學業表現來說，這個結果確實在預期之內。

某種程度上，這也是這次推甄讓我最有感觸的地方。我花了很多時間累積實務經驗，卻沒有把最基本的學業成績顧好。

順帶一提，兩天面試我都穿著黑色西裝和皮鞋，或許交大不喜歡我穿得這麼正式吧，哈哈。不過這次的面試經驗還是讓我學到很多，也讓我重新思考，過去這幾年究竟把時間花在了什麼地方。

## 一、一些背景：從資訊科到資管系

在開始分享推甄內容之前，我想先簡單介紹一下自己的背景。我高中讀的是資訊科，也曾經是技能競賽的選手。當時接觸比較多的是硬體、MCU、網路相關技術，也參加過一些硬體領域的競賽，拿過前幾名的成績。所以在進入大學之前，我一直以來比較熟悉的，其實是硬體與網路相關的領域。

不過後來進入大學資管系，整個學習方向突然變得非常不一樣。從原本寫 MCU、接觸電路和網路設備，突然變成以軟體開發、資訊系統與管理相關課程為主。老實說，我當時有點水土不服。一方面是自己原本熟悉的東西不太一樣，另一方面是大學的課程少了很多我以前很喜歡的內容，例如電學、數位邏輯等等。這些課程其實是我高中滿喜歡的東西，突然少了這一塊，多少有點失落。因此，我在大學前期其實過得沒有很開心，也花了一些時間適應新的學習環境。

### 1. 從技能競賽到 ICPC

其實最一開始，我還是想繼續參加技能競賽，只是學校的參賽名額已經由其他教授的學生取得，所以我就沒辦法繼續比了，哈哈。但因為還是很想參加比賽，後來才轉去參加 ICPC 等競程相關的比賽。只是結果沒有想像中理想，最後大概就是拿到台中分區的參加獎，哈哈。

這件事情當時其實讓我滿挫折的。因為高中時期，我在硬體相關競賽曾經拿過不錯的成績，所以多少會希望自己到了大學，也能在競賽中有所表現。但實際參加 ICPC 之後，才發現演算法競賽跟我高中熟悉的技能競賽，根本是完全不同的東西。高中主要不是在練競程，到了大學卻要面對大量演算法、資料結構與解題技巧，確實需要花很多時間重新累積。

我記得自己的學長曾經拿過金手獎第一名，學弟也拿過金手獎的好成績，印象中應該有第三名左右。看到學長的成果，我會想，自己也想變得跟他們一樣厲害；看到學弟的表現，則是覺得「哇靠，牛逼啊」，有一種長江後浪推前浪的感覺。因為我知道那背後需要投入多少時間練習，所以是真的很佩服他們。

也許有人會覺得，競賽沒有拿到成績，不就是自己沒有認真練習嗎？為什麼要一直說時間不夠？某種程度上，我也不能否認這個說法。競賽就是需要大量的練習，沒有投入足夠的時間，本來就很難拿到好成績。

但我當時確實同時在做太多事情了。課業、專案、工作、研究，以及自己想學習的技術，每一項都在消耗時間。有時候我真的覺得，自己根本就是在超負荷前行。不是不想練習，而是每天能夠使用的時間就只有那麼多。現在回頭看，或許當時就應該更早做出取捨，而不是一直覺得自己還可以再多做一點。

### 2. 補習、研究所考試與差距 14 分的台大

其實我也不是完全沒有準備過研究所考試。大二、大三那段時間，我有利用暑假去補習研究所的考試科目。當時想說，既然自己在大學有些基礎科目沒有學得很好，那就透過補習重新把演算法、資料結構等內容補起來。

但實際上，整個準備過程非常零碎。因為同時還有其他專案和事情要處理，時間常常被切成一小段一小段。今天可能讀了一些內容，隔幾天卻又因為專案或工作中斷，等到下次有時間回來讀，前面學過的東西又忘記了一部分。讀書的進度很難持續，也很難進行完整的複習。

我印象特別深刻的是，最後一次考台大研究所時，距離目標分數差了 14 分。14 分其實也差滿多的啦。但說真的，我又覺得沒有那麼遙遠。因為當時回頭看演算法與資料結構的題目，有幾題其實是自己看錯、想錯，或是沒有發揮好。

那時候一直會想，如果自己當初再細心一點，把那些原本有機會拿到的分數拿下來，結果會不會不一樣？但這也只是事後的假設。就算那幾題真的寫對了，也不代表最後一定會錄取。只是距離自己想要的結果並沒有遠到完全看不到希望，所以反而更加遺憾。

### 3. 大學期間的工作與專案經歷

這裡也要特別感謝以前參加比賽時認識的學長，讓我有機會參與這些工作，接觸實際的專案與工程問題。大學期間，我參與過政府基金資訊平台的前端開發與 E2E 自動化測試、登記抽系統的登入串接與後端 API 開發，以及銀行內部系統的翻新，接觸了 Angular、ASP.NET Web API、資料庫整合與測試流程。後來也參與[保哥的龍蝦課](https://learn.duotify.com/courses/githubclaw)相關 AI Agent 平台開發，處理 Bot 互動、記憶與任務流程，以及 Cloudflare Workers 的架構重構和部署，前後大約參與了四個專案。在擔任計畫助理期間，我也幫學校開發了捐款系統。另外，我也持續負責 Cisco 網路設備、Wi-Fi、Hyper-V 與機房伺服器的維運，使用 OpenVAS 進行弱點掃描，並建置 Guacamole 遠端管理環境。從軟體開發到基礎設施，這些都是我在課業、專題與研究之外持續投入的工作。

## 二、專題與研究經歷

除了前面提到的工作與專案，我也投入了不少時間在畢業專題與論文研究上。這兩篇論文我都是第二作者，不過大部分的實驗與論文撰寫工作是由我負責。

### 1. 畢業專題：ISO 27001、RAG 與 Kubernetes

**整合 AI 推論與雲原生技術之智慧化資安管理平台**

![[Assets/Note/Tech/116 學年度陽明交大資工推甄心得：我做了很多事，好像也什麼都沒有做/智慧化資安管理平台架構.png]]

我的專題是與學校老師合作，主要目標是建立一套能輔助 ISO 27001 資訊安全管理流程的系統。當初的想法，是希望利用 RAG 降低資安人員在文件查詢、管理與作業上的負擔。系統除了 RAG 之外，也有設計核准、拋轉、狀態追蹤、稽核管理等功能。現在回頭看，當時還沒有那麼明確的 Agentic AI 概念，但有些設計方向其實已經有點接近現在的 Agentic Workflow。

而我自己主要投入了大量的系統架構與工程實作。例如：

- Kubernetes 的整體部署架構。
- LLM 服務如何部署，以及各個服務之間如何解耦。
- Storage、Volume 的規劃。
- 多租戶（Multi-tenancy）架構。
- 透過 Argo CD 管理不同 Namespace 的部署。
- 不同租戶如何配置與使用 LLM。
- Python 應用程式的封裝與 Container Image 建置。
- 還有使用 RabbitMQ 等等的

其中有一部分需要將 Python 程式封裝成 Binary 再放入 Image。老實說，我真的不太想這樣做，但當時因為一些限制，最後還是採用了這個方式。

整個系統原本預計提供給臺科大、宜蘭大學、東華大學，以及敝校使用。當時的想法，是希望多個學校能共用同一份 Code，不用每間學校都重新開發一套；如果某間學校有客製化需求，再從共同的程式碼切出分支處理。希望以同一套系統支援不同學校，也是我當時設計多租戶架構的原因。只是後來在跨校合作與溝通上遇到一些問題，因此後續實際的推動情況，我也不是很清楚。

這個專題從頭到尾做了一年多。真的只能說，工程量非常浩大。那段時間每天的生活幾乎就是：打開電腦 → 修 Bug → 睡覺 → 隔天繼續修 Bug。無限循環。最後光是整理出來的文件就有三百多頁，而且還是刪減過的版本。

不過這個專題後來也有一些不錯的成果。我們在 TaNET 研討會獲得了最佳論文獎，也參加了資訊應用服務創新競賽，拿到資安組第三名。

但現在回頭看，我心裡其實有一些複雜的感受。因為做了這麼多事情，確實累積了很多實務經驗，也有競賽與論文成果。只是我漏掉了最基本的一件事：成績。當時覺得有機會做這樣的大型專案很難得，所以想盡可能做好。但現在想想，有些地方真的不知道值不值得。

### 2. 另一篇論文：從中醫 RAG 到 Knowledge Graph 與 Agentic AI

另外一篇論文，目前還在 Review 階段。這篇是我之前考完研究所、心情非常低落的時候，跟另一位老師合作開始做的研究。

一開始，我們要解決的是中醫領域的 RAG 問題。但做下去才發現，這個領域真的沒有想像中簡單。中醫存在大量專有名詞，而且同一個概念可能有不同稱呼，還涉及中醫與西醫之間的疾病名稱對應。在我們當時的資料與實驗設定下，單純使用 BM25 或 Dense Retrieval，檢索效果並不理想。因此，我後來開始思考，是否有其他方法能夠處理這個問題。最後採用的方向，比較接近 Agentic AI。我們使用經過醫師認可的 Knowledge Graph（KG），其中包含藥材、病症，以及中西醫疾病名稱的對應關係。再搭配 Agent Skills，讓 Agent 能夠根據問題需求，查詢相關知識與資訊。實作上有使用 Copilot SDK 與 Pi Agent。實際測試後，效果比我原先想像中還好。最後再請醫師進行評分與評估，整理結果、進行統計分析，並撰寫成論文。

但這篇論文最花時間的，其實不只是 Agent 的設計。從最初的 IRB、Raw Data Cleaning，到後面的資料整理、模型微調與 Hyperparameter Tuning，都投入了非常多時間。尤其資料清理那一段，真的花了超級久。後續還要建立 Agent Harness、設計實驗、分析結果，以及把整份論文整理出來。我一開始使用 LaTeX 寫作，後來又需要轉成 Word 方便與老師協作。整個過程大概花了四個月左右。當時主要是為了趕 IEEE Journal of Biomedical and Health Informatics（J-BHI）的 Special Issue，這本期刊收錄於 SCIE，依 IEEE 2026 年 9 月公布的期刊清單，JIF 分區為 Q1。目前論文仍在審查中，所以最後會有什麼結果，還不能確定。

另外，目前也有跟老師討論下一篇 Journal 的方向。希望能進一步研究像 Jev 這類 Decision Model，是否能改善 Agentic RAG 的效率與決策過程。不過這部分還在討論與規劃階段，應該就是另一篇 Journal 的事情了。

## 三、丁組：系統與網路管理實務

### 1. 電腦測驗

丁組跟往年一樣，會先進行測驗。這次總共有 46 題，我寫了 39 題。題目橫跨網路、系統管理、Kubernetes、資安、AI、HPC 等領域，考的東西其實滿廣的，而且不是全部都只問名詞，有不少題目需要實際理解系統的運作流程。以下是我還記得的內容，部分題目的名稱或細節可能有些出入。

**基礎網路與系統管理**

最前面有一些比較基本的題目，例如 NAT、DNS、Git 操作等等。另外也考了：

- `systemd` 的服務設定，以及 Ansible 的使用。
- Git worktree 的操作與應用。
- 路由備援協定，例如 HSRP、VRRP、GLBP 等相關技術。
- SNMP 的監控機制，包含 Polling 與主動通知（Trap／Inform）的差異。
- 交換器相關技術，以及光纖傳輸的損耗計算。
- 多機交換或交換器架構相關題目，以及 IEEE 802.1w、802.1Q 等標準的比較。

這些東西有些是工作或專案會接觸到的，有些則是過去準備網路相關技術時讀過的內容。

**Kubernetes 與可觀測性**

Kubernetes 的題目包含：

- Kubernetes 的核心 Components。
- StatefulSet 與 PVC 有什麼差別，也就是那個千年老問題。
- 執行 `kubectl run` 並指定 nginx Image 之後的運作流程。
- Kubernetes 的可觀測性（Observability）。
- 利用 AI 管理 Kubernetes Cluster 的工具。

其中 AI 管理 Kubernetes 的那個工具，我當下真的沒有看過，所以沒有寫出來。另外可觀測性本身還有一大題，這部分需要對系統監控的概念有一定理解。

**資安與 Web**

這部分包含：

- Cookie、Session 與 JWT 的設計差異及取捨。
- JWT 相關的驗證與安全問題。
- 資安事件的描述與分析。

由於那段時間剛好遇到所謂的「黑色十月」，資安事件特別多，因此也有相關題目。我當時選擇寫的是 HTTP2Shell。

**Mail Server**

Mail Server 大約有四到五題，我應該寫了三題左右。印象比較深的是，直接給一段郵件紀錄，要求分析郵件的轉送流程。另外還有：

- Log Server 應該放在哪裡，才能方便監控。
- 郵件 Forwarding 可能造成什麼問題。
- Mail Server 要遷移到 Kubernetes 內部，應該怎麼進行。
- 遷移到 Kubernetes 的過程會遇到哪些風險與問題。

這裡的遷移題，主要背景是丁組要把 Mail Server 遷移到 Kubernetes 內部，所以才問到遷移方式，以及過程中可能遇到的風險與問題。這部分其實相當偏實務，而且題目不只是問你懂不懂 SMTP，而是要知道實際營運 Mail Server 可能遇到什麼事情。

**HPC、LLM 與 AI 工具**

另外還有一大題跟 HPC 有關，剛好跟我的專題和論文研究有部分重疊。其中包含 vLLM、模型量化，以及根據模型參數量與數值精度估算記憶體需求之類的題目。這大題印象中有三到四個小題，我寫了兩題。AI 工具相關也有一大題，包含 WebMCP 等技術名詞與應用概念。

整體來說，這次考試考得非常廣。46 題裡面我作答了 39 題，有幾題可能是當下真的想不起來，所以就沒有硬寫。但其實大部分題目都是我曾經看過，甚至實際接觸過的東西。比較可惜的是，有些題目我可能知道概念，卻沒有把答案描述得足夠完整或精確。

我覺得這也是系統領域很困難的地方。從 Network、Linux、Kubernetes、Security、Mail Server，到後來的 AI 與 HPC，真的有太多東西需要學習，而且每個領域都可以繼續往下鑽得非常深。我的背景本來就跨了很多領域，有些知識太久沒碰會忘記，我也實在沒辦法。腦袋真的不夠裝了。不過至少就當下來說，我認為自己已經 did my best 了。

### 2. 面試流程與學長提問

丁組的面試有安排大約 30～60 秒的自我介紹。這個時間其實相當短，基本上只能快速介紹自己的背景與經歷，沒有太多時間展開說明專案或研究細節。接著就是針對筆試內容、專案經驗及相關技術進行問答。

學長一開始就先問了我 JWT 相關的問題，中間也穿插了幾題我在電腦測驗中回答的內容。其中他有提到，我 Mail Server 的題目寫得還可以，接著問我有沒有實際管理 Mail Server 的經驗。但我在公司主要接觸的是 Microsoft Entra ID 相關服務，沒有真正負責過完整的 Mail Server 管理，所以我就直接回答沒有。

後面也聊到了一些專案經驗，包含政府相關專案、電商抽獎系統等等。還有問我為什麼能回答某些系統管理相關問題。我大概回答，之前有參加比賽，加上平常會一直使用命令列，也會自己查資料、研究系統，因此多少累積了一些相關知識。

另一個印象很深刻的問題是：「如果你的同事用 AI 寫出很爛的 Code，你會怎麼辦？」我當時回答，以現在 AI 的能力來看，很多時候 AI 產生品質不佳的程式碼，是因為需求本身沒有被定義清楚。換句話說，有時候不是 AI 不會寫，而是人沒有把問題說清楚。當然，這不代表所有 AI 產生的問題都能歸咎於需求，程式碼還是需要經過測試、Review 與驗證。這邊我也提到了自己跟公司一起開發的 GitHubClaw 專案。

整體來說，學長面試比較像是根據筆試內容和履歷，進一步確認到底有沒有實際接觸過相關技術。

### 3. 教授面試

丁組面試的老師中，其中一位是[謝秉均老師](https://www.cs.nycu.edu.tw/members/detail/pinghsieh)。其實第一天就已經有教授坐在面試現場了，只是第二天跟老師的互動更多。一開始有位老師直接問我：「聽說你網路不錯？」我回答自己大概有 CCNP 的程度，部分 CCIE 範圍也有接觸。結果老師下一句直接問：「那 DPDK 你有沒有用過？」這題我真的沒有。我過去的網路經驗比較偏 Cisco 設備與網路架構，沒有實際操作過 DPDK，所以就直接回答沒有。面試時也有被問到：「你是同時工作，又同時上課嗎？」我回答：「對。」

接著老師又問，如果希望網卡達到最佳吞吐量，會怎麼設定？這題我覺得自己沒有回答得很好。一開始聽到吞吐量，我先想到的是 LACP、Link Aggregation 那一類的技術。但後來釐清問題，才知道老師想討論的是網卡與作業系統層級的效能調校。我有回答到 Kernel 與網卡相關設定，但沒有把完整的調校方向有條理地說出來。現在回頭想，如果能從 NIC Offloading、RSS、IRQ Affinity、Ring Buffer、Kernel Network Stack 等方向切入，整體回答應該會更完整。不過面試當下真的不是那麼容易，尤其現場有兩位老師輪流提問，問題的順序有點混亂。

另一題是：「你怎麼保證 Code Quality？」我當時舉了公司將 Cisco 設定檔轉成 IaC、透過 Ansible 管理，再使用 Pull Request 讓主管 Review 的例子，主要是因為剛好接續上提問的網路相關的問題。但事後回想，我覺得這題也沒有回答得很好。因為我其他專案其實有做過 Unit Testing、Integration Testing、CI/CD，以及弱點掃描等工作，當下卻沒有全部講出來。

另一位老師則問我有沒有使用過 AI Coding Tools。這題我就比較熟悉了。我大概從最早自己手寫程式碼開始講，後來一路接觸 Claude Code、`CLAUDE.md`，再到 Skills、MCP，以及 Spec-Driven Development（SDD）。像這次的推甄資料，我也是使用 OpenSpec 搭配 LaTeX 撰寫了多份，算是把這些工具用在準備升學資料上。AI 開發工具這幾年的變化真的非常快，我自己也一直在嘗試不同的工作流程。只是面試時間有限，沒辦法把所有經驗都完整講完。

## 四、戊組：校務資訊系統技術與實務

### 1. 筆試

戊組跟丁組不太一樣，考的是 30 題選擇題。整體而言，我覺得相對簡單。前面大約四題跟考古題有點像，主要是《資通安全管理法》與個人資料保護相關內容。我自己猜應該是全對啦，不然以我的在校成績和校名，可能就不會出現在備取名單裡面了，好好笑。當然，這只是我自己的猜測，實際答對幾題我也不知道。

後面則包含：

- 系統設計與資訊安全的 Best Practices。
- LLM、MCP 等技術名詞。
- Training Batch 的作用。
- JWT 的驗證機制。
- 其他系統管理相關概念。

### 2. 教授面試

戊組面試的老師中，其中一位是[謝旻錚老師](https://www.cs.nycu.edu.tw/members/detail/_101)。戊組跟丁組一樣，也有 30～60 秒左右的自我介紹。自我介紹結束後，就開始進入教授提問。戊組面試的重點就比較偏向我的實際專案經驗。老師問了幾個問題，例如：

- 過去做過的專案規模有多大？
- 一個專案通常有幾個人合作？
- 有沒有同時跟很多人一起開發？
- 某個專案實際提供多少使用者使用？

這些問題看起來不難，但我覺得其實滿難回答的。因為我自己做的很多專案，通常是由我主導開發；而公司的專案則會有 PM 或老闆負責整體規劃。因此，專案規模、合作方式與責任分工，其實每個案子都不太一樣。

其中一個專案是銀行內部系統的重構案。老師有問我實際提供多少人使用，但我只知道它是銀行內部使用的系統，並不掌握最後的確切使用人數，所以沒辦法提供準確數字。

接著有問到我的論文，我大概花了一分鐘介紹研究內容。也有問我之後的規劃，包含工作與升學要怎麼安排。另一位女老師也問我：「你是同時工作，又同時上課嗎？」我回答：「對。」

最後有一題我覺得非常重要。「如果你錄取了，要怎麼處理成績這一塊？」我當時回答，自己在大三的時候有去補習。老師主要在意的是演算法相關的成績。這部分其實也是我一直知道的問題。我相信敝校的學弟和同學們多少都知道演算法之間的恩怨情仇，好好笑。而是我知道自己大學期間真的忙了太多事情，沒有把足夠的時間分配給課業。這不是什麼很好的藉口。只是當時的我，真的很難兩全其美。後來面試就差不多結束了。

## 五、另外兩個志願：資聯與智慧科學暨綠能學院碩士聯招

除了丁組和戊組，我另外也申請了交大資聯，以及智慧科學暨綠能學院碩士班聯合招生。這兩個志願最後都是不錄取。老實說，我看到結果的時候並沒有太意外。因為這兩個招生管道都會審查在校成績，而我的成績並不算好。

這幾年我把不少時間投入工作、競賽、系統開發與研究，但這些經歷到底能不能在推甄審查中彌補成績上的不足，本來就沒有一定的答案。更何況，其他申請者可能同時具備很好的學業成績、專題成果與研究經驗。

我也不認為自己做過一些實務專案，就理所當然應該得到錄取機會。只是這兩個結果，確實讓我重新意識到自己過去沒有顧好成績的代價。不過，實際的不錄取原因仍然只有審查委員知道。我能做的，就是記錄結果，接受自己的不足，然後想辦法改善。

## 六、如果能重來，我會怎麼選？

這次推甄結束後，我其實一直在想這件事情。從高中接觸硬體、MCU 與網路，到大學進入資管系，開始學習軟體開發、系統管理、Kubernetes、LLM、RAG，以及後來的 Agentic AI。中間也參加過技能競賽、ICPC，準備過研究所考試，做過公司專案、畢業專題與論文研究。回頭看，這幾年真的做了滿多事情的。

但是，我也很清楚，自己的成績並沒有跟上這些經歷。尤其是一些資訊工程領域很核心的科目，例如演算法，我沒有交出理想的成績。這其實也是我從準備研究所考試，到這次推甄，一直反覆遇到的問題。以前在高中，我比較擅長的領域是硬體與網路，到了大學卻需要重新適應資訊工程與軟體開發的相關知識。我也不是完全沒有想過把演算法與資料結構補起來。補習、考研、參加 ICPC，其實某種程度上都是自己想嘗試突破這一塊的方式。但最後都沒有達到原本想要的結果。

現在回頭看，我覺得有一個很大的問題，就是我一直沒有真正做好取捨。我什麼都想學，什麼都想做，也很容易因為遇到有趣的技術，就繼續往下研究。但人的時間終究是有限的。把時間分配給一個專案，就意味著少了一些時間能夠拿來準備考試；投入一場競賽，也代表必須犧牲其他事情的進度。這些代價當下不一定會感受到，但時間一久，就會慢慢累積。

我不認為做專案、參加競賽或研究論文是不值得的。這些經驗讓我學到很多課堂上不一定能接觸到的東西，也讓我知道一個真正需要交付的系統，跟學校作業之間有多大的差別。但我現在也逐漸理解，會實作一個系統，與能夠深入理解、分析、證明背後的原理，並不是同一件事情。對研究所而言，基礎學科、研究能力與長期學術潛力，也都是很重要的事情。

如果今天能夠重來一次，我想我會做出不太一樣的選擇。我寧願把論文的研究成果累積得更扎實一些，同時把大學成績顧好，而不是把自己有限的時間分散在這麼多不同的專案與技術領域。或許這才是交大更想要的人才。當然，我不知道教授們實際是怎麼評分的，也不知道這次備取的名次究竟是受到什麼因素影響。

過去我常常會覺得，只要自己能夠把東西做出來，能解決實際的問題，就代表自己具備一定程度的技術能力。這個想法並沒有完全錯。但這次推甄也提醒我，實務能力、學術基礎與研究成果，本來就應該是能夠相互支持的東西，而不是必須犧牲其中一個去換取另一個。如果未來還有機會繼續走研究這條路，我希望自己能夠把這部分補起來。但也或許，我已經沒有機會繼續往學術方向走了，最後還是會放棄自己原本想走的那條路。想到這裡，心裡其實滿難受的，但是也沒有辦法，時間不等人了。

## 七、最後

這次丁、戊組面試比較可惜的地方，是沒有談到我的畢業專題，畢竟那是我投入了一年多的工作。

目前拿到的結果是丁組備取 3、戊組備取 6，另外兩個志願則是不錄取。是不是能夠順利遞補，還要看最後的招生情況。

我其實不知道該怎麼形容現在的心情。因為這不是一個完全沒有希望的結果，但也不是一個能讓自己安心的結果。如果最後真的有機會錄取，那當然很好。如果沒有，我想這次的經歷至少也讓我知道，自己還有哪些不足的地方。

只是說真的，做了一年多的專題、四個月的研究，再加上工作與其他專案，最後回頭看到成績這一塊，還是會覺得有點遺憾。尤其想到之前台大研究所考試差了 14 分，現在推甄又落在一個不知道能不能遞補的位置。這種好像每一次都差一點的感覺，真的滿難受的。

不知道當初如果少做幾個專案，多花一點時間在課業與研究上，今天的結果會不會不一樣。但人生大概就是這樣，很多選擇都只能事後才知道代價。

從高中到現在，也經歷了不少失敗和挫折。看著學長在自己擅長的領域持續前進，會讓我想變得跟他們一樣厲害；看到學弟拿到很好的成績，則是覺得「哇靠，牛逼啊」，真的有一種長江後浪推前浪的感覺。像是學弟的科展專題拿到好成績，後來又在國際科展獲獎，最後保送交大；還有學長進了師大資工、學弟進了北科資工，都讓我很佩服。再看看同學們，有的上了北科資財、北科資工、台科資安，碩班都快過完一個學期了，自己卻好像還在原地踏步，想想心情也是滿複雜的。

我知道他們也付出了很多努力，只是看著他們，難免也會回頭想，自己這幾年一路忙到現在，到底走到了哪裡。畢竟我也曾經很希望自己能夠做到那些事情。

只是到目前為止，很多結果跟自己原本想像的都不太一樣。說完全不在意是騙人的。這些挫折累積到現在，有時候真的覺得有點累了。但不管結果如何，這些都是我自己做過的選擇，也應該由自己承擔。

人生大概就是這樣吧。沒有什麼事情一定是完美的，也不是每一次努力都能換到想要的結果。很多時候只能接受、改進，然後繼續往前走。Keep going.

只是說真的，從高中到大學、從競賽到考研，挫折一個接著一個累積起來，有時候我真的覺得自己快有點扛不住了。尤其是當自己明明花了很多時間做事，最後卻沒有拿到原本期待的成果時，那種落差其實滿難消化的。但不管怎麼樣，這些都是我一路走過來的經歷。也正因為這些事情，後來我選擇繼續累積專案與研究經驗，並嘗試透過研究所推甄，看看自己還有沒有其他機會。

我想現在能做的，大概就是接受這些不完美，重新調整自己的方向，然後繼續往前走。不一定要每件事情都做到最好，也不需要什麼都同時完成。至少希望以後的自己，能夠更清楚知道什麼事情值得投入，以及什麼時候應該停下來。

以我目前對頂大推甄的了解與這次申請的感受，在校成績的影響真的很大，尤其是純書審的管道，會讓我覺得其他經歷很難補上成績的差距。即使有面試，成績也可能成為被追問、影響評價的地方，就像這次老師問到我的演算法成績一樣。

最後，可能還是會再考一次研究所吧。只是有些重要的內容又有點忘記了，如果真的要再考，也得重新撿起來複習。這次的推甄結果，不論最後有沒有錄取，都會是我重新思考自己未來方向的一個轉折點。至少這次，我真的已經盡力了。但願那些失眠的無數個夜晚，和每一個熬過的夜，終究能換來一個好結果。Keep going.
