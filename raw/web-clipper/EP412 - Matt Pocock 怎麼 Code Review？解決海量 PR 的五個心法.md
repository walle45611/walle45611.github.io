### 心法四：人只守回不去的門

**8:27** · 但就算 PR 品質變好了，數量還是很多， 你不可能每一個都仔細看。

**8:31** · 第四個心法要回答的是，哪些 PR 一定要你自己看。

**8:34** · Matt 借用了亞馬遜內部常用的一個說法， 叫單向門跟雙向門。

**8:38** · 你要用 AWS 的一個說法來想 PR： 它是單向門，還是雙向門？

**8:48** · 你手上大部分的 PR 都是雙向門， merge 之後隨時都可以再撤回來。

**8:54** · 這是當軟體工程師的美好福利， 土木工程師可沒有，對吧？

**8:59** · 土木工程師做的大多是單向門， 你一出錯，那座橋就垮了。

**9:04** · 雙向門的意思是，改動可以很容易撤回。

**9:09** · 不過哪些算單向門，可能比你想的複雜。

**9:14** · 有可能一個很簡單的改動， 不小心寄了一封信給六萬個人， 那它就是單向門， 你要非常非常仔細地 review。

**9:24** · 牽涉到昂貴的遷移、或可能掉資料？

**9:26** · 那就是單向門，給我把那個 PR 看到爛。

**9:29** · 我們用白話整理一下。

**9:30** · 雙向門就是 merge 之後還推得回來的改動， 出錯了 revert 就好，大部分的 PR 都是這種。

**9:35** · 單向門是關上就回不去的改動，像寄出去的信收不回來， 刪掉的資料救不回來。

**9:39** · 麻煩的是，單向門不一定長得很大。

**9:42** · 改一個設定，就可能讓系統寄信給六萬個人。

**9:44** · 所以判斷的方法，是問這個改動出錯之後還能不能撤回。

**9:48** · Matt 新做的 pr 這個 skill， 就把這件事寫進每一個 PR 的描述裡。

**9:53** · 最底下有一塊叫合併風險，寫兩件事： 這是單向門還是雙向門，還有 blast radius， 也就是出錯的時候會影響到多少使用者、資料或系統。

**10:02** · 套到你的流程，就是在你的 PR 模板裡加這一塊。

**10:04** · 每一個 PR 先標它是哪一種門。

**10:06** · 雙向門掃過去就好，你的時間全部留給單向門。

**10:08** · 最後一個心法，我覺得是整場最值得帶走的。

### 心法五：review 的是系統

**10:11** · 你在 review 一個 PR 的時候， 看的其實不只是這一次的 code。

**10:15** · Matt 認為，你在幫 agent 打造一個工作環境， 而那個環境才是真正產出 code 的東西。

**10:21** · 我們是一起在幫 agent 打造工作環境。

**10:25** · 你應該把產生 code 的那套流程， 看得跟 code 本身一樣重要。

**10:31** · 換句話說，你在做人的 review 時， 你看的不只是 code， 你在 review 的是產生它的那套系統。

**10:37** · 這裡的原則是：同一句意見不要寫兩次。

**10:42** · 不要在兩個 PR 裡抓到 agent 犯同一種錯。

**10:46** · 他的意思是，如果你在兩個不同的 PR 裡， 抓到 agent 犯同一種錯，那問題不在這兩個 PR， 在產生它們的那套系統。

**10:54** · 下一次，應該讓系統自己擋掉這個錯。

**10:57** · 為了做到這一點，Matt 做了一個 skill 叫 retro， 也就是回顧。

**11:00** · 你把做完的工作丟給它，可以是一次對話、一個 PR， 或是過去一週所有的 PR。

**11:05** · 它會建議你加哪一個自動檢查，或者規範要怎麼更新。

**11:09** · retro 裡還有一個原則：一個錯誤如果是機械性的， 就寫成自動檢查，不要多寫一條規則， 因為規則 agent 可能不讀，檢查每一次都會跑。

**11:17** · 套到你的流程，就是每個禮拜跑一次回顧， 同一句意見出現第二次，就把它變成檢查。
