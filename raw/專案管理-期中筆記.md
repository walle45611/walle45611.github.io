# 一、組織結構與人員管理

## 1. 功能經理是什麼？

**功能經理（Functional Manager）**就是「部門主管」或「職能主管」。

例如：

| 部門 | 功能經理 |
|---|---|
| 資訊部 | IT 經理、資訊主管 |
| 財務部 | 財務經理 |
| 人資部 | HR 經理 |
| 行銷部 | 行銷經理 |
| 工程部 | 工程主管 |

功能經理的重點是：**管人、管專業、管部門資源。**

專案經理的重點是：**管專案目標、進度、成本、品質、交付成果。**

一句話記法：

> 功能經理管「部門與人」，專案經理管「專案與成果」。

---

## 2. 功能型組織 Functional Organization

功能型組織是依照部門專業分工，例如資訊部、人資部、財務部、行銷部。

在功能型組織中，員工主要向功能經理報告，專案經理的權力通常很低。

| 項目 | 功能型組織 |
|---|---|
| 權力最大者 | 功能經理 |
| PM 權力 | 很低 |
| 成員歸屬 | 原本部門 |
| 資源取得 | 需要透過部門主管協調 |
| 優點 | 專業分工清楚、技術累積穩定 |
| 缺點 | 跨部門協調慢、專案優先度低 |

考題關鍵字：

- 成員仍屬於各部門。
- 專案經理只是協調者。
- 資源由部門主管分配。
- PM 權限小，很難直接指揮成員。

常見陷阱：如果題目說「專案經理需要某位工程師協助，但工程師直屬 IT 部門主管」，不要選 PM 直接命令工程師或命令功能經理。比較好的做法是：**與功能經理協調資源與優先順序**。

---

## 3. 專案型組織 Projectized Organization

專案型組織是以專案為核心運作，團隊成員通常專職投入專案，直接向專案經理報告。

| 項目 | 專案型組織 |
|---|---|
| 權力最大者 | 專案經理 |
| PM 權力 | 很高 |
| 成員歸屬 | 專案團隊 |
| 資源取得 | PM 控制力高 |
| 優點 | 決策快、目標一致 |
| 缺點 | 資源可能重複配置，專案結束後成員歸屬可能不明 |

考題關鍵字：PM 權限高、團隊專職參與專案、成員主要向 PM 報告、專案結束後團隊可能解散。

---

## 4. 矩陣型組織 Matrix Organization

矩陣型組織是功能型與專案型的混合。成員通常同時受到功能經理與專案經理管理。

| 類型 | PM 權力 | 功能經理權力 | 判斷方式 |
|---|---:|---:|---|
| 弱矩陣 Weak Matrix | 低 | 高 | 比較像功能型，PM 像協調者 |
| 平衡矩陣 Balanced Matrix | 中 | 中 | PM 與功能經理權力接近 |
| 強矩陣 Strong Matrix | 高 | 中低 | 比較像專案型，PM 權力較高 |

一句話記法：

> 矩陣組織就是「一個員工，兩個老闆」。

這裡的「兩個老闆」通常是：

- 功能經理：負責部門、專業、績效、人員管理。
- 專案經理：負責專案目標、工作安排、交付成果。

---

## 5. 雙重回報 Dual Reporting Relationship

雙重回報是矩陣組織最常見的情況。

例子：小明是資訊部工程師，被派到 ERP 導入專案。

| 管理者 | 管什麼 |
|---|---|
| IT 功能經理 | 小明的職涯、考績、技術標準、部門任務 |
| ERP 專案經理 | 小明在 ERP 專案中的任務、進度、交付成果 |

這就是雙重回報。

考題處理原則：遇到雙重回報，不要選「硬壓」、「命令」、「跳過主管」這類答案。比較好的答案通常是協調功能經理、釐清角色與責任、建立責任分派矩陣、溝通資源優先順序，必要時依正式程序升級。

---

## 6. RACI 責任分派矩陣

RACI 常用於釐清誰負責、誰核准、誰諮詢、誰被通知。

| 字母 | 英文 | 中文 | 意義 |
|---|---|---|---|
| R | Responsible | 負責執行 | 真正做事的人 |
| A | Accountable | 當責／最終負責 | 對結果負最終責任的人 |
| C | Consulted | 諮詢 | 事前需要詢問意見的人 |
| I | Informed | 通知 | 事後需要被告知的人 |

如果題目出現權責不清、不知道誰該做、多人重複做同一件事、任務沒人負責，優先想到：**RACI / RAM 責任分派矩陣**。

---

## 7. Maslow 需求層次理論

Maslow 是激勵理論，常用來判斷團隊成員的需求層次。

由低到高：

| 層級 | 中文 | 英文 | 例子 |
|---:|---|---|---|
| 1 | 生理需求 | Physiological Needs | 薪水、休息、吃飯 |
| 2 | 安全需求 | Safety Needs | 工作穩定、安全環境 |
| 3 | 社交需求 | Social Needs | 團隊歸屬、人際關係 |
| 4 | 尊重需求 | Esteem Needs | 被肯定、被表揚、職位 |
| 5 | 自我實現 | Self-Actualization | 成長、挑戰、實現理想 |

一句話記法：

> 低層需求沒滿足，高層激勵通常沒效果。

例如員工擔心明天被裁員，你跟他談「自我實現」通常沒用。他會先在意安全需求，而不是理想人生。

# 二、PERT、三點估計、Network Diagram、Critical Path

## 1. 三點估計 Three-Point Estimating

三點估計會給三個數字：

| 符號 | 中文 | 英文 | 意義 |
|---|---|---|---|
| O | 樂觀時間 | Optimistic | 最順利時需要多久 |
| M | 最可能時間 | Most Likely | 正常情況下需要多久 |
| P | 悲觀時間 | Pessimistic | 最糟但合理情況下需要多久 |

---

## 2. PERT / β 分配公式

如果題目寫 PERT、β 分配、Beta Distribution、Program Evaluation and Review Technique，就使用：

```text
Expected Duration = (O + 4M + P) / 6
```

例題：最樂觀工期 4 天，最可能工期 7 天，最悲觀工期 16 天，使用 PERT，預期工期是多少？

```text
O = 4
M = 7
P = 16

Expected Duration = (4 + 4×7 + 16) / 6
                  = (4 + 28 + 16) / 6
                  = 48 / 6
                  = 8 天
```

答案：**8 天**

你原本的錯誤想法：

```text
(4 + 7 + 16) / 3 = 9
```

這是 **三角分配 / 簡單平均**，不是 PERT。

---

## 3. PERT vs 三角分配

| 方法 | 公式 | 使用時機 |
|---|---|---|
| PERT / β 分配 | `(O + 4M + P) / 6` | 題目寫 PERT、β 分配 |
| 三角分配 Triangular | `(O + M + P) / 3` | 題目只說三點平均，沒有寫 PERT |

考試口訣：

> 看到 PERT，M 乘 4。沒有 PERT，才考慮普通平均。

---

## 4. Network Diagram 網路圖

Network Diagram 是把活動的先後順序畫成圖，用來找出專案總工期與關鍵路徑。

| 元素 | 意義 |
|---|---|
| Activity 活動 | 要完成的工作 |
| Duration 工期 | 活動需要的時間 |
| Dependency 相依關係 | 活動之間的先後順序 |
| Path 路徑 | 從開始到結束的一串活動 |
| Critical Path 關鍵路徑 | 總工期最長的路徑 |

---

## 5. Critical Path 關鍵路徑

關鍵路徑是：

> 從開始到結束，總工期最長的那條路徑。

注意：不是最短，是最長。因為所有活動都要完成，最長那條路徑決定專案最快什麼時候能完工。

例子：

| 路徑 | 工期 |
|---|---:|
| A → C → E | 4 + 8 + 3 = 15 |
| B → C → E | 7 + 8 + 3 = 18 |
| B → D → F | 7 + 5 + 4 = 16 |
| A → C → F | 4 + 8 + 4 = 16 |
| B → C → F | 7 + 8 + 4 = 19 |

最長的是：

```text
B → C → F = 19 天
```

所以 Critical Path 是 **B → C → F**。

---

## 6. Float / Slack 浮時

Float / Slack 是活動可以延遲，但不影響專案總完工日期的時間。

| 活動類型 | 浮時 |
|---|---:|
| 關鍵路徑上的活動 | 0 |
| 非關鍵路徑上的活動 | 大於 0 |

一句話記法：

> 關鍵路徑沒有緩衝，一延誤就拖累整個專案。

---

## 7. 關鍵路徑題目的解題步驟

1. 找出所有從「開始」到「結束」的路徑。
2. 把每條路徑的活動工期加總。
3. 最大值就是專案最短完工時間。
4. 最大值那條路徑就是 Critical Path。
5. 如果要縮短專案工期，要壓縮 Critical Path 上的活動才有效。

---

## 8. 時程壓縮：Crashing vs Fast Tracking

| 方法 | 中文 | 做法 | 代價 |
|---|---|---|---|
| Crashing | 縮程法／趕工 | 增加資源縮短工期 | 成本增加，可能影響品質 |
| Fast Tracking | 快速跟進 | 原本先後順序改成重疊進行 | 風險增加，可能重工 |

| 題目情境 | 答案方向 |
|---|---|
| 願意增加成本換時間 | Crashing |
| 活動可以部分重疊 | Fast Tracking |
| 要縮短總工期 | 優先處理 Critical Path 活動 |

---

## 9. 資源撫平 vs 資源平滑

| 項目 | 資源撫平 Resource Leveling | 資源平滑 Resource Smoothing |
|---|---|---|
| 主要限制 | 資源限制 | 時間限制 |
| 做法 | 重新調整任務，避免資源超載 | 在浮時內調整任務 |
| 是否改變關鍵路徑 | 可能會 | 不會 |
| 是否延後完工日期 | 可能會 | 不會 |
| 適用情境 | 資源不夠、資源過載 | 想讓資源使用更平均 |

一句話記法：

> 撫平會動日期，平滑不動日期。

# 三、Kanban、User Story Map、逐步精進完善

## 1. Kanban 看板

Kanban 是一種視覺化管理流程的方法。

最基本看板：

| To Do | Doing | Done |
|---|---|---|
| 待辦 | 進行中 | 已完成 |

### Kanban 核心重點

| 重點 | 說明 |
|---|---|
| 視覺化工作 | 讓所有人看到工作狀態 |
| 限制 WIP | 限制同時進行中的工作量 |
| 管理 Flow | 讓工作流程順暢 |
| 找出瓶頸 | 看哪一欄卡最多 |
| 持續改善 | 根據流程問題調整 |

WIP = Work in Progress，進行中的工作。如果 Doing 欄限制 WIP = 3，代表最多只能有 3 件工作同時進行。第 4 件不能硬塞進來，要先完成目前工作。

| 題目描述 | 優先想到 |
|---|---|
| 工作太多同時進行 | 限制 WIP |
| 不知道工作卡在哪 | 視覺化流程 |
| 任務堆在某一欄 | 找瓶頸 |
| 團隊一直開始新工作但很少完成 | 限制 WIP |
| 想改善流程效率 | 管理 Flow |

常見陷阱：Kanban 不是叫大家同時做更多事。Kanban 是讓團隊少做一點「同時進行」，多完成一點「真正交付」。

---

## 2. User Story 使用者故事

使用者故事常見格式：

```text
As a [role], I want [feature], so that [benefit].
```

中文：

```text
身為 [某種使用者]，我想要 [某功能]，以便 [達成某價值]。
```

例子：

```text
身為顧客，我想要查詢過去訂單，以便快速再次購買。
```

好的 User Story 不是只寫功能，而是要包含使用者價值。

---

## 3. User Story Map 使用者故事地圖

User Story Map 是把使用者旅程、任務、故事與優先順序整理成地圖。

| 層級 | 內容 |
|---|---|
| 上層 | 使用者活動 / 使用者旅程 |
| 中層 | 使用者任務 |
| 下層 | 使用者故事 |
| 橫向 | 使用流程順序 |
| 縱向 | 優先順序 |

例子：訂餐系統

| 使用者活動 | 瀏覽餐點 | 加入購物車 | 結帳 | 查看訂單 |
|---|---|---|---|---|
| 高優先 | 看菜單 | 加入餐點 | 付款 | 查詢狀態 |
| 中優先 | 搜尋餐點 | 修改數量 | 使用優惠券 | 取消訂單 |
| 低優先 | 收藏店家 | 推薦餐點 | 分期付款 | 評價餐點 |

用途：看清使用者流程、排優先順序、規劃 MVP、規劃 Release、避免漏需求。

| 項目 | Product Backlog | User Story Map |
|---|---|---|
| 性質 | 需求清單 | 使用者旅程地圖 |
| 排列方式 | 優先順序清單 | 橫向流程 + 縱向優先順序 |
| 重點 | 要做哪些需求 | 使用者如何完成目標 |
| 用途 | 管理待辦事項 | 規劃產品版本與 MVP |

---

## 4. 逐步精進完善 Progressive Elaboration

逐步精進完善是專案的特性之一。

意思是：

> 專案初期資訊不完整，規劃會隨著專案進展逐漸變詳細。

它不是亂改，也不是 PM 沒規劃好，而是專案本來就有不確定性。

| 錯誤理解 | 正確理解 |
|---|---|
| 一開始沒規劃好，所以後面一直改 | 資訊逐漸明朗，所以計畫逐步細化 |
| 代表 PM 沒能力 | 代表 PM 正在管理不確定性 |
| 等於範疇蔓延 | 不等於，範疇蔓延是未受控增加範疇 |
| 只有敏捷才有 | 預測式專案也會有 |

---

## 5. Rolling Wave Planning 滾波規劃

滾波規劃就是：

> 近的規劃細，遠的規劃粗。

| 時間距離 | 規劃詳細程度 |
|---|---|
| 本週 | 很詳細 |
| 下個月 | 中等詳細 |
| 半年後 | 粗略規劃 |

一句話記法：

> 遠粗近細，邊做邊清楚。

# 四、其他考前高機率補充

## 1. 專案與作業差異

| 項目 | 專案 Project | 作業 Operation |
|---|---|---|
| 時間性 | 有開始與結束 | 持續、重複 |
| 目標 | 創造獨特成果 | 維持日常運作 |
| 結果 | 新產品、新系統、新流程 | 穩定產出 |
| 例子 | 導入 ERP、新院區建置 | 每月薪資、日常客服 |

一句話記法：

> 作業讓組織活著，專案讓組織進化。

---

## 2. 專案黃金四角

專案目標常見四大構面：

| 構面 | 意義 |
|---|---|
| 範疇 Scope | 要做什麼、不做什麼 |
| 時間 Time | 何時完成 |
| 成本 Cost | 預算與資源 |
| 品質 Quality | 產出是否符合標準 |

重點：這四者互相制約。如果範疇增加，通常時間或成本會增加。如果時間被壓縮，成本可能增加，品質也可能受影響。

---

## 3. 阻礙目標達成的三大因素

| 因素 | 意義 | 處理方式 |
|---|---|---|
| 議題 Issues | 已經發生的問題 | 立即處理 |
| 變更 Changes | 需求或條件改變 | 評估影響並走變更流程 |
| 風險 Risk | 尚未發生但可能發生 | 預先規劃應對 |

一句話記法：

> 議題是已發生，風險是還沒發生，變更是需求改變。

---

## 4. 溝通管道公式

公式：

```text
溝通管道數 = n(n - 1) / 2
```

其中 n 是人數。

例子：如果有 8 個利害關係人：

```text
8(8 - 1) / 2 = 8×7 / 2 = 28
```

所以溝通管道是 28 條。

---

## 5. 準備金：應變準備金 vs 管理準備金

| 項目 | 應變準備金 Contingency Reserve | 管理準備金 Management Reserve |
|---|---|---|
| 對象 | 已知的未知 Known Unknowns | 未知的未知 Unknown Unknowns |
| 控管者 | PM | 高層／老闆 |
| 是否在成本基準內 | 通常包含於成本基準 | 不包含於成本基準 |
| 用途 | 已識別風險的應對 | 未預期重大事件 |

一句話記法：

> 已知風險 PM 管，未知大事老闆管。

---

## 6. EVA 實獲值分析基本公式

| 指標 | 公式 | 判讀 |
|---|---|---|
| CV 成本差異 | EV - AC | 大於 0：省錢；小於 0：超支 |
| SV 進度差異 | EV - PV | 大於 0：超前；小於 0：落後 |
| CPI 成本績效 | EV / AC | 大於 1：成本效率好；小於 1：成本效率差 |
| SPI 進度績效 | EV / PV | 大於 1：進度效率好；小於 1：進度效率差 |

一句話記法：

> 差異看正負，指標看 1。

# 五、錯題導向總複習表

| 錯題主題 | 必背重點 | 看到題目要想到 |
|---|---|---|
| 功能型組織 | 功能經理權力最大，PM 權力低 | 部門主管、原部門、PM 協調 |
| 矩陣組織 | PM 與功能經理共享權力 | 雙重回報、協調資源 |
| 雙重回報 | 一個人同時向 PM 與功能經理負責 | 釐清責任、RACI、協商 |
| Maslow | 生理 → 安全 → 社交 → 尊重 → 自我實現 | 低層未滿足，高層激勵效果差 |
| PERT | `(O + 4M + P) / 6` | 題目寫 PERT / β 分配 |
| 三角分配 | `(O + M + P) / 3` | 題目沒有 PERT，只說平均 |
| Network Diagram | 列出所有路徑並加總 | 找最長路徑 |
| Critical Path | 最長路徑，Float = 0 | 決定專案總工期 |
| Crashing | 加資源縮短工期 | 成本增加 |
| Fast Tracking | 活動重疊執行 | 風險與重工增加 |
| Resource Leveling | 可能延後完工 | 資源限制 |
| Resource Smoothing | 不延後完工 | 在浮時內調整 |
| Kanban | 視覺化、限制 WIP、找瓶頸 | 不要一直開新工作 |
| User Story Map | 使用者旅程 + 優先順序 | 規劃 MVP / Release |
| Progressive Elaboration | 計畫逐步細化 | 不是亂改，也不是範疇蔓延 |

# 六、考前 30 分鐘速讀版

## 必背 1：組織權力

```text
功能型：功能經理最大，PM 最小
矩陣型：PM 與功能經理共享權力
專案型：PM 最大
```

## 必背 2：PERT

```text
PERT = (O + 4M + P) / 6
普通平均 = (O + M + P) / 3
```

## 必背 3：Critical Path

```text
從開始到結束，總工期最長的路徑
關鍵路徑 Float = 0
壓縮工期要壓縮關鍵路徑上的活動
```

## 必背 4：Kanban

```text
視覺化工作
限制 WIP
管理 Flow
找出瓶頸
持續改善
```

## 必背 5：Progressive Elaboration

```text
早期資訊不足，後續逐步細化
不是亂改
不是範疇蔓延
搭配 Rolling Wave Planning：遠粗近細
```

## 必背 6：議題、變更、風險

```text
議題：已經發生
風險：尚未發生
變更：需求或條件改變
```
