- DeepSeek-V4：CSA、HCA 與 mHC 的架構位置
  - source links:
    - https://fe-static.deepseek.com/chat/transparency/deepseek-V4-model-card-EN.pdf
    - https://huggingface.co/docs/transformers/main/en/model_doc/deepseek_v4
  - 1 句話核心概念：DeepSeek-V4 的 CSA/HCA 是 Hybrid Attention Architecture 的兩種長距注意力路徑，而 mHC 是 residual connection 的修改，三者不是同一層級的機制。
  - 重點：
    - 官方 model card 將 Hybrid Attention Architecture 與 Manifold-Constrained Hyper-Connections 分開列為架構創新。
    - CSA 以較低壓縮率建立 compressed entries，再由 indexer 選取重要區塊；HCA 使用更高壓縮率並讓壓縮後 entries 以 dense attention 參與。
    - Hugging Face 實作文件列出 CSA 預設 compression rate `m=4`、HCA 預設 `m'=128`，並保留 sliding-window local branch。
    - DeepSeek-V4 文件標示最大 context 為 1M tokens；長 context 效率來自壓縮與局部／長距混合，而不是單純傳統 full attention。

- DGX Spark、Gemma 4 與 vLLM serving
  - source links:
    - https://docs.nvidia.com/dgx/dgx-spark/dgx-spark.pdf
    - https://docs.nvidia.com/dgx/dgx-spark-porting-guide/dgx-spark-porting-guide.pdf
    - https://forums.developer.nvidia.com/t/gemma-4-models-which-vllm-version-any-prs-spotted/365490/43
    - https://forums.developer.nvidia.com/t/gemma-4-day-1-inference-on-nvidia-dgx-spark-preliminary-benchmarks/365503/20
    - https://github.com/kelnei/vllm-gemma4
    - https://docs.nvidia.com/deeplearning/frameworks/vllm-release-notes/rel-26-04.html
  - 1 句話核心概念：DGX Spark 的優勢是 128 GB unified memory 帶來模型容量與 POC 彈性，但 273 GB/s 記憶體頻寬與 ARM/UMA 特性使 serving 需要特別重視量化、KV cache、runtime 相容性與實測吞吐。
  - 重點：
    - NVIDIA 文件確認 DGX Spark 為 Grace Blackwell Arm SoC、128 GB unified memory；Porting Guide 列出 256-bit memory interface 與 273 GB/s bandwidth。
    - Gemma 4 NVFP4 可利用 Blackwell 原生低精度能力降低權重占用；社群實測顯示模型「跑得動」與實際 decode 速度是兩個不同問題。
    - `kelnei/vllm-gemma4` 提供 DGX Spark / Blackwell 的 vLLM Compose 實例，支援 Gemma 4 31B 的 262,144-token context、FP8 KV cache、tool parser 與 reasoning parser。
    - 該 repo 目前也記錄 vLLM 0.27.x 與特定 Transformers 版本的相容性 workaround，說明 runtime、模型架構與 dependency version 必須一起驗證，不能只照單一啟動參數複製。

- Tailscale container `/dev/net/tun` 與 userspace networking
  - source links:
    - https://tailscale.com/docs/concepts/userspace-networking
    - https://tailscale.com/docs/features/containers/docker/docker-params
    - https://tailscale.com/docs/reference/tailscaled
  - 1 句話核心概念：容器沒有 `/dev/net/tun` 時，普通 kernel TUN 模式的 `tailscaled` 無法建立介面；可改用 `--tun=userspace-networking`，避免依賴 TUN device。
  - 重點：
    - Tailscale 官方文件明確指出 `/dev/net/tun` 缺失是容器環境常見限制，而 userspace mode 專門用來處理這類情境。
    - CLI 可用 `tailscaled --tun=userspace-networking ...` 啟動；官方 Docker image 的 `TS_USERSPACE` 參數與此等價。
    - userspace mode 以 userspace netstack / proxy 方式運作，因此與真正建立 `tailscale0` kernel interface 的行為不同，應依應用程式流量需求選擇 SOCKS5、HTTP proxy 或具 TUN device 的 kernel 模式。

## 知識串聯

今天的內容可以串成同一條工程主線：模型本身只是系統的一層。DeepSeek-V4 顯示 attention 與 residual architecture 需要分層理解；DGX Spark / Gemma 4 顯示硬體容量、記憶體頻寬、量化與 runtime version 共同決定 serving；Pi 與 Tailscale 則進一步把問題推到 harness、tool discovery、provider、權限與網路邊界。對 Agent 系統而言，「能跑」與「可控、可重現、可安全部署」是不同層級的要求。
