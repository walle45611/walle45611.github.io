### Remote-access VPN hairpin 與內網存取

- 今天檢視了「人在公司內網時，再連回同一台對外 VPN gateway 的 public endpoint」這類拓撲。
- 這類流量屬於 hairpin / inside-to-own-public-IP 類型，和真正從 Internet 進入 remote-access VPN 的封包路徑不同；NAT、介面方向、IPsec policy 與平台實作都可能影響是否成功。
- Cisco 的 ASA 官方文件把 VPN hairpin 明確視為特殊案例：需要允許 intra-interface traffic，並配合正確 NAT 規則。這能支持「hairpin 不是一般 remote-access 流量」的概念，但該文件是 ASA，不應直接當成 Cisco IOS router 的逐條設定指南。
- 在實務設計上，若裝置已位於可信任的公司 LAN，通常應直接走 LAN route 存取內部主機，而不是刻意繞回 remote-access VPN gateway。

  - https://www.cisco.com/c/en/us/td/docs/security/asa/asa912/configuration/firewall/asa-912-firewall-config/nat-reference.html

### Tailscale subnet router / overlay routing

- Tailscale 官方文件確認 subnet router 的用途是讓 tailnet 裝置存取「沒有直接安裝 Tailscale」的私有網段裝置。
- Linux subnet router 的基本流程是：開啟 IP forwarding、以 `--advertise-routes` 宣告可達 CIDR、在 admin console 核准 routes；macOS、Windows、Android、iOS 與 tvOS 預設接受 subnet routes。
- Route injection 與 access control 是兩個不同層次：要真正連通，既要有已核准並注入的 route，也要有允許該流量的 ACL / grant。
- 對今天討論的 Raspberry Pi subnet-router 架構而言，這代表可以把遠端裝置到內網的存取交給 overlay routing，而不必維持傳統「外面手動連 VPN、進公司後手動斷 VPN」的操作模式。
- 但同一台裝置若同時位於本地 LAN、又接受與 LAN 重疊的 subnet route，路由選擇仍要實測。Tailscale 官方 troubleshooting 特別指出：當本地 LAN 與 subnet router 都能到同一目的地時，裝置可能有兩條路徑，且在某些情況下會偏好 subnet router。因此「人在內網一定直接走 LAN」不能當成無條件保證；需要看實際 routing table、route specificity 與 client 設定。
- references:

  - https://tailscale.com/docs/reference/route-injection
  - https://tailscale.com/docs/reference/troubleshooting/connectivity/connect-lan-failure
  - https://tailscale.com/docs/reference/devices-without-tailscale

## 知識串聯

今天的主線是「傳統 remote-access VPN 與 overlay routing 的路徑控制差異」。傳統 VPN 的問題常落在 interface、NAT、IPsec policy 與 hairpin path；Tailscale subnet router 則把私有網段透過 tailnet 宣告成可路由範圍，降低手動切換 VPN 的需求。不過 overlay 並不消除底層 routing 規則：當本地 LAN 與 advertised subnet 重疊時，仍要以實際 routing table 驗證流量到底走 LAN 還是 subnet router。
