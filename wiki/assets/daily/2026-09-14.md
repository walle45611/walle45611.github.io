- LLM 推論引擎：從 token、KV Cache 到 Agent Loop
  - source: `raw/LLM 推理引擎到底是怎么工作的：从一个 token 到 KV 缓存、连续批处理，再到 Agent Loop 如何把 GPU 榨干.md`
  - source link: https://x.com/shao__meng/status/2098783138118041760?s=46
  - 1 句話核心概念：LLM 推論效能不只由單次模型前向運算決定，還高度依賴 scheduler 如何分配請求、token 預算與 KV Cache，以及 continuous batching、PagedAttention、chunked prefill 和 prefix caching 如何配合實際負載。
  - 3 到 5 個重點：
    - Prefill 建立 prompt 狀態，decode 逐 token 延續生成；常見 compute-bound／memory-bound 分類是理解負載的近似框架，不是所有硬體與批次條件下的絕對結論。
    - Continuous batching 會在每一步重新組批，讓已完成請求釋出資源給等待中的請求，降低靜態批次被最慢請求拖住的浪費。
    - PagedAttention 用固定大小 blocks 管理 KV Cache，降低為最大長度預留記憶體造成的碎片與浪費；來源中的碎片率數字屬二手轉述，未獨立核對測量條件。
    - Chunked prefill 讓長 prompt 分多次進入排程，避免一次 prefill 長時間阻塞既有 decode；它改善的是排程干擾，不代表新請求 TTFT 必然降低。
    - Agent loop 常形成長前綴、短新增尾段的重複請求，prefix caching 可重用相同前綴的 KV，但必須滿足引擎支援、前綴相容與快取未淘汰等條件。

- 圖解 KV Cache——DS V4.1-Flash 的制勝秘密
  - source: `raw/图解 KV Cache——DS V4.1-Flash的制胜秘密.md`
  - source link: https://x.com/wquguru/status/2099119760248389730?s=46
  - 1 句話核心概念：KV Cache 優化要分開看每筆資料大小、序列長度、跨層副本、注意力讀取與儲存位置，不能把架構壓縮、量化、分頁、稀疏讀取與 offload 全部視為同一種「壓縮」。
  - 3 到 5 個重點：
    - 自回歸推論保留歷史 token 的 K/V，可避免每一步重新產生歷史 K/V，但注意力仍需要讀取歷史狀態；K/V 重用不等於完整 attention 成本消失。
    - 容量與頻寬要分開分析：稀疏選取可以降低每步注意力讀取量，但若完整 KV 仍保存，就不等於儲存容量同步下降。
    - GQA、MLA、滑動窗口、跨層復用屬模型／架構層手段；分頁、前綴共享與 offload 屬系統層手段，解決的瓶頸並不相同。
    - 來源對 DeepSeek V4.1-Flash 的 CED、CSA2、階層索引、約 900 bytes/token 等描述，本次 summary 明確保留為作者主張與近似估算，未視為已核實官方規格。
    - 快取量化和權重量化是不同對象；降低 KV 儲存精度，也不代表後續 attention 必然以相同低精度完成計算。

### NVIDIA DGX Spark Hardware Overview

- https://docs.nvidia.com/dgx/dgx-spark/hardware.html
- 本次重新核對的官方規格：128 GB LPDDR5x unified system memory、273 GB/s memory bandwidth，以及最高 1 PFLOP FP4（使用 sparsity 的理論峰值）。
- 這些數字可用於 Roofline 的硬體上限判讀，但 `273 GB/s` 與 `1 PFLOP FP4 sparse` 分別代表記憶體與特定低精度稀疏計算的理論上限，不能直接當成任意 LLM workload 的實測速度。
- 今天複習 Roofline 時的核心式子是 `P_attainable = min(P_peak, BW × arithmetic_intensity)`；batch 1 的逐 token decode 若每步需要大量讀取模型權重而每 byte 可做的運算有限，通常會落在 memory-bound 一側。
- FLOP 是運算次數，FLOPS 是每秒運算速率；容量估算、理論 FLOPs 與實際 latency／tokens per second 應分開看。
- 本次沒有取得足以核實特定「Gemma 4 31B」模型規格的官方頁面，因此沒有把未確認的模型參數或實測值寫入日報。
